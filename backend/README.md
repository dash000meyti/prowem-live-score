# PROWEM Live Score API

Backend implementation for the **PROWEM Full-Stack Live Score take-home task**.

This service manages a small four-team football tournament, accepts score changes, recalculates standings immediately, and broadcasts confirmed tournament updates to connected clients in real time.

The repository is organized as two sibling applications:

```text
prowem-live-score/
├── backend/
└── mobile/
```

This README documents the **backend** application. The Flutter client lives in `../mobile`.

---

## The Task

The take-home task is to build a small full-stack live-score application for a football tournament.

The required scenario is:

- exactly **4 teams**
- a standard **round-robin tournament**
- therefore **3 rounds** and **6 total matches**
- a PHP/MySQL backend
- endpoints to validate and store match results
- real-time calculation of:
    - points
    - goal difference
    - ranking
- an API exposing tournament standings and match updates
- a mobile client, with Flutter as the recommended implementation
- real-time synchronization when a score changes
- a visible standings animation where rows move when a goal changes the ranking

The implementation in this repository uses:

- **Laravel 13** for the API
- **MySQL 8.4** for persistence
- **Redis** for queues
- **Laravel Reverb** for WebSocket broadcasting
- **Flutter** for the mobile application

The REST API remains the source of truth. WebSocket events provide low-latency updates between REST snapshots.

## Backend Architecture

The backend intentionally uses a **lightweight layered Laravel architecture** rather than a textbook Clean Architecture implementation.

```text
HTTP Request
     │
     ▼
Controller
     │
     ▼
Form Request
     │
     ▼
Action
     │
     ├──────────────► Domain Services
     │
     ▼
Eloquent / MySQL
     │
     ▼
TournamentUpdated
     │
     ▼
Redis Queue
     │
     ▼
Laravel Reverb
     │
     ▼
Connected Clients
```

Application structure:

```text
app/
├── Actions/
│   └── Matches/
│       └── UpdateMatchResult.php
│
├── Enums/
│   └── GameStatus.php
│
├── Events/
│   └── TournamentUpdated.php
│
├── Exceptions/
│   ├── InvalidGameStatusTransition.php
│   └── TeamAlreadyInLiveMatch.php
│
├── Http/
│   ├── Controllers/
│   │   └── Api/
│   ├── Requests/
│   └── Resources/
│
├── Models/
│   ├── Game.php
│   └── Team.php
│
└── Services/
    └── Tournament/
        ├── RoundRobinScheduler.php
        └── StandingsCalculator.php
```

Responsibilities are separated intentionally:

- **Controllers** own HTTP concerns.
- **Form Requests** validate transport input.
- **Actions** coordinate application-level mutations and transactions.
- **Services** contain reusable tournament calculations and domain rules.
- **Models** represent persistence.
- **Resources** define the public API representation.
- **Events** transport committed state changes to the real-time layer.

No repository abstraction, CQRS layer, event sourcing, or module framework is introduced because the domain is small and Eloquent already provides the persistence abstraction required for this exercise.

## Tournament

The seeded tournament contains exactly four teams:

```text
Juventus
Inter
AC Milan
AS Roma
```

A standard round-robin schedule produces:

```text
4 teams
3 rounds
2 matches per round
6 matches total
```

Fixtures are generated by `RoundRobinScheduler` using the **circle method** rather than being hard-coded.

The scheduler is independently unit tested for:

- number of matches
- number of rounds
- no self-match
- unique team pairs
- one match per team per round
- every team meeting every other team exactly once
- balanced home/away distribution
- odd team counts with a bye
- invalid tournament sizes

## Match Model

The PHP model is named `Game` because `match` is a reserved PHP keyword.

The database table is still named:

```text
matches
```

A match contains:

```text
id
home_team_id
away_team_id
round_number
home_score
away_score
status
kickoff_at
created_at
updated_at
```

Scores are nullable by design.

This distinction is important:

```text
NULL - NULL
```

means:

> the match has not been played yet

while:

```text
0 - 0
```

means:

> a real scoreless draw

---

## Match States

Supported states:

```text
scheduled
in_play
finished
```

Allowed result transitions:

```text
scheduled → in_play
scheduled → finished

in_play   → in_play
in_play   → finished

finished  → finished
```

The following rollback transitions are intentionally rejected:

```text
in_play  → scheduled
finished → scheduled
finished → in_play
```

`finished → finished` is allowed so a completed result can still be corrected.

---

## Live Match Invariant

A team may participate in **at most one `in_play` match at a time**.

For example:

```text
Juventus vs Inter      LIVE
Juventus vs AC Milan   LIVE   ❌
```

is rejected.

However two disjoint live matches are valid:

```text
Juventus vs Inter      LIVE
AC Milan vs AS Roma    LIVE   ✅
```

The backend is authoritative for this rule.

The Flutter client may disable obviously invalid actions for better UX, but the invariant is always enforced by the backend.

---

## Standings

Standings are **derived from match state** and are not persisted in a separate table.

This avoids duplicated state and eliminates the possibility of stored standings drifting away from match results.

Matches contributing to standings:

```text
in_play   ✅
finished  ✅
scheduled ❌
```

Points use standard football scoring:

```text
win  = 3 points
draw = 1 point
loss = 0 points
```

Ranking order:

```text
1. Points descending
2. Goal difference descending
3. Goals for descending
4. Team ID ascending
```

The final `team_id` comparison is only a deterministic fallback when all football statistics are equal.

Because live matches already count toward standings, a single goal can immediately change ranking order.

That behavior is what drives the animated standings movement in the Flutter client.

## Result Update Flow

The mutation endpoint is:

```http
PATCH /api/matches/{game}/result
```

Example request:

```json
{
  "home_score": 2,
  "away_score": 1,
  "status": "in_play"
}
```

The application then:

```text
1. validates the HTTP request
2. opens a database transaction
3. acquires the tournament mutation lock
4. locks the target match
5. validates the state transition
6. validates live-match team availability
7. updates the score/status
8. recalculates standings
9. commits the transaction
10. generates synchronization metadata
11. dispatches TournamentUpdated
12. returns the same confirmed snapshot to the HTTP client
```

The HTTP result and WebSocket event carry the same logical update.

---

## Concurrency and Consistency

Result changes are treated as **tournament-level mutations**.

The current application contains one tournament, so all tournament team rows are locked in deterministic ID order before a match mutation proceeds.

The target match is then loaded using `FOR UPDATE`.

This provides a serialization point for result changes.

The purpose is to prevent two concurrent updates from producing:

```text
Match payload from state A
+
Standings payload from state B
```

Standings are recalculated **inside the same database transaction** while the tournament mutation lock is held.

The real-time event is dispatched only after the transaction has committed.

If the system is extended to support multiple tournaments, the serialization lock should move to the owning tournament row rather than locking every team globally.

---

## Database Integrity

Important invariants are also enforced by MySQL as defense in depth.

Valid statuses are restricted to:

```text
scheduled
in_play
finished
```

Score state must be consistent with match state:

```text
scheduled
→ home_score IS NULL
→ away_score IS NULL

in_play / finished
→ home_score IS NOT NULL
→ away_score IS NOT NULL
```

Therefore these states are rejected even if application logic is bypassed:

```text
scheduled + 1-0       ❌
in_play + NULL-NULL   ❌
finished + NULL-NULL  ❌
status = cancelled    ❌
```

while these are valid:

```text
scheduled + NULL-NULL ✅
in_play + 0-0         ✅
finished + 2-1        ✅
```

Scores use unsigned small integers and API validation restricts them to:

```text
0 .. 65535
```

## Match Update Response

A successful result mutation returns synchronization metadata together with the confirmed match and recalculated standings.

Conceptually:

```json
{
  "data": {
    "update_id": "uuid",
    "occurred_at": "2026-08-10T07:00:00.000000Z",
    "match": {
      "id": 1,
      "home_team_id": 1,
      "away_team_id": 2,
      "home_score": 2,
      "away_score": 1,
      "status": "in_play"
    },
    "standings": []
  }
}
```

`update_id` is also included in the corresponding WebSocket event.

This allows clients to deduplicate:

```text
HTTP confirmation
+
WebSocket event generated by the same mutation
```

instead of applying one mutation twice.

## Error Semantics

The API distinguishes between invalid input and valid input that conflicts with domain state.

### HTTP 422 — Validation error

Used when the request itself is invalid.

Examples:

- missing score
- negative score
- score above `65535`
- unsupported request status
- trying to send `scheduled` through the result mutation endpoint

Laravel's validation error structure is returned.

### HTTP 409 — Domain conflict

Used when the request is valid but conflicts with the current tournament state.

Stable machine-readable codes are included.

Invalid state transition:

```json
{
  "message": "Cannot transition a match from \"finished\" to \"in_play\".",
  "code": "INVALID_MATCH_STATUS_TRANSITION",
  "errors": {
    "status": [
      "Cannot transition a match from \"finished\" to \"in_play\"."
    ]
  }
}
```

Team already involved in another live match:

```json
{
  "message": "One of the teams is already playing another live match.",
  "code": "TEAM_ALREADY_IN_LIVE_MATCH",
  "errors": {
    "status": [
      "One of the teams is already playing another live match."
    ]
  },
  "conflict": {
    "match_id": 3
  }
}
```

Clients should use `code` for application behavior and treat `message` as human-readable text.

## Real-Time Updates

Laravel Reverb provides the WebSocket server.

Tournament updates use the public channel:

```text
tournament
```

Event name:

```text
tournament.updated
```

Conceptual payload:

```json
{
  "update_id": "uuid",
  "occurred_at": "2026-08-10T07:00:00.000000Z",
  "match": {},
  "standings": []
}
```

Broadcasting flow:

```text
Laravel transaction committed
        │
        ▼
TournamentUpdated
        │
        ▼
Redis queue
        │
        ▼
Queue worker
        │
        ▼
Laravel Reverb
        │
        ▼
Flutter clients
```

The event uses a **public channel**, so no private-channel authorization endpoint is required.

---

## REST vs WebSocket Responsibilities

The WebSocket connection is not treated as the permanent source of truth.

The intended client strategy is:

```text
Initial connection
    → GET /api/tournament

Normal operation
    → tournament.updated events

Reconnect / recovery
    → GET /api/tournament again
```

This makes disconnect recovery simple and prevents missed WebSocket events from permanently corrupting client state.

## Why Standings Are Not Persisted

The tournament contains only four teams and six matches.

Standings are cheap to calculate and are entirely derived from match results.

Persisting them would introduce another state representation that would need synchronization with matches.

For this domain:

```text
matches = source data
standings = projection
```

Recalculating the projection after every mutation is simpler and safer.

---

## Why There Is No Repository Layer

Eloquent already provides the persistence boundary required by this application.

Introducing interfaces such as:

```text
GameRepositoryInterface
TeamRepositoryInterface
```

would add indirection without solving a current problem.

For a much larger application, a separate persistence abstraction might become useful.

For this task, it would mostly be architectural ceremony.

---

## Why There Is No Tournament Table

The task defines one fixed tournament containing exactly four teams.

The current solution therefore models the application as a single tournament.

This keeps the implementation proportional to the requirements.

If multiple tournaments are introduced later, a `tournaments` table would become the natural owner of:

- teams / tournament participation
- matches
- tournament configuration
- tournament-level mutation locking

The current concurrency lock would then move to the relevant tournament row.

---

## Why Result Updates Use an Action

A score update performs more than a simple model write.

It coordinates:

```text
transaction
locking
state-transition validation
live-match invariant validation
persistence
standings recalculation
event creation
```

That orchestration belongs in an application Action rather than in a Controller or Eloquent model.

---

## Design Trade-Offs

This implementation intentionally prioritizes:

```text
correctness
clear domain rules
small architecture
deterministic behavior
reconnect safety
testability
```

over adding features outside the task.

Notable choices:

- standings are recalculated instead of persisted
- REST remains the source of truth
- WebSocket events carry full updated standings
- event payloads have a stable `update_id`
- result mutations are serialized at tournament level
- domain conflicts use HTTP `409`
- transport validation uses HTTP `422`
- feature tests use MySQL instead of SQLite
- public Reverb channels avoid unnecessary authorization infrastructure
- the seeder preserves existing tournament state
- no speculative repository/CQRS/event-sourcing architecture is introduced

## Production Considerations

This repository is a take-home implementation, not a complete production deployment.

For a production system I would additionally consider:

- authentication and authorization for result mutations
- restricted Reverb allowed origins
- HTTPS / WSS termination
- secret management
- request rate limiting
- observability and structured logging
- queue monitoring
- deployment-specific health/readiness checks
- multiple tournament ownership
- database backup and recovery
- CI quality-gate execution
- horizontal Reverb scaling if required
- stronger audit history for score corrections

These are intentionally outside the current task unless required by the deployment environment.
